# Project Objective: What are you trying to model? Include a brief description that would give someone unfamiliar with the topic a basic understanding of your goal.

For our model, we decided to model a spanning tree of weather stations. The weather stations were represented by nodes and the edges between them represented a direct link of communication. Our goal was to create this without cycles while still having all of the nodes be connected, and the scope for this project was for the stations to be able to communicate with each other about whether a storm is approaching or not. The root/central station is the only node to receive the information directly about the storm prediction and then that information propagates from parent to child. Ultimately, our end goal was for every station to eventually receive the same information. My partner and I found this idea interesting because one user loves weather and weather modeling and the other has an interest in entrepreneurship and business. Thus, weather station communication is very important because it can save lives by propagating storm information to help prepare for destruction and evacuation. Pivoting, from an entrepreneurship perspective, our project models a centralized network where there is a single point of control (root node - AtlantaCentralStation) where all of the information originates and flows outwards from. This type of communication style is very relevant in the business world as this tree structure ensures that every node receives the same information (stemming from a “command”) without redundancy or miscommunication.  

# Model Design and Visualization: Give an overview of your model design choices, what checks or run statements you wrote, and what we should expect to see from an instance produced by the Sterling visualizer. How should we look at and interpret an instance created by your spec? Did you create a custom visualization, or did you use the default?

For our design choices, the model represents a weather station connection network rooted at AtlantaCentralStation, where each station has a parent edge that defines this hierarchy as well as a passStorComing edge that demonstrates the way in which national storm information is propagated downstream within our tree, producing two parallel arrows between each pair of nodes. Our validStations predicate enforces that our tree has no cycles, exactly one parent per non-root station, at most 2 direct children of Atlanta. Additionally, defineTree hardcodes two direct chains from the root (AtlantaCentralStation), defineStormEdges handles the storm edges by setting each station’s passStormComing equal to its parent with none at the root as the root does not have a parent node. 
At the bottom of our main file, the run statement combines all three of these predicates for 8 stations in order to produce one single valid instance. When looking at our instance produced by the Sterling visualizer, the relationship between parent and children nodes should be evident, as well as the manner in which storm propagation is handled. Additionally, we did create and customize our own visualization in order to both add personal touch to this project and emphasize the fact that each of these weather stations is in a different state, creating a nationwide network. 

# Signatures and Predicates: At a high level, what do each of your sigs and preds represent in the context of the model? Justify the purpose for their existence and how they fit together. 
	The sigs present in our model are: 
Station: the main sig that represents any weather station in the network with two fields (parent: defines the hierarchical structure by pointing to the station directly above it and passStormComingInfo that mirrors the parent edge to represent the direction in which the storm information is flowing). 
AtlantaCentralStation extends Station and is the root node with no parent, making it the origin of the storm data with centralStationStormInfo that points to either StormTrue or StormFalse to represent whether a storm is predicted or not. 
Georgetown, Philadelphia, NewYork, NewOrleans, Denver, LosAngeles, and Dallas all extend Station as one-sigs representing each individual station in the network. 
StormBool is an abstract sig with StormTrue and StormFalse acting as a boolean representation of the binary storm predication. 

The predicates in our model are:
validStations is a pred that enforces the architectural structure of the tree and defines valid tree as: a node cannot be its own parent, no cycles, exactly one parent person non-root station, and AtlantaCentralStation has at most two children. 
defineTree directly hardcodes the specific relationships between all stations and directly constructs the two roots.
defineStormEdges sets the passStormComing equal to parent for every non-root and none at the root, which guarantees storm information flows in the same direction as the tree’s hierarchy. 

Together these signatures and predicates clearly model our initial idea with the sigs defining what should exist in the model while the predicates define the entire structure and behavior of the model. 

# Testing: What tests did you write to test your model itself? What tests did you write to verify properties about your domain area? Feel free to give a high-level overview of this.

– We wrote a mixture of tests for each of our 3 predicates : validStations , defineTree, and defineStormEdges. (test expects + assertions)

validStations : We wrote a mix of asserts and test expectations in order to make sure the key functions of a station were honored. We wanted to check that the root station never has a parent because it's very important for the propagating storm logic of the central station being the only one to receive storm information, and it wouldn't need a parent station to feed information back into it, creating a cycle. We also wanted to honor the properties of a spanning tree and ensure that there were cycles, so we made sure that no station can point to itself as a parent. We decided to use a text expect rather than an assertion because we wanted to ensure that Forge couldn't find another instance where a station was its own parent. Testing reachability was extremely difficult for us in validStations so we relied on testing it in the other predicates suits and looking at the visualizer. Lastly we made sure to include tests for over-constraint, under-constraint, and exclusion + inclusion tests.

defineTree: define tree as a predicate was an optional modeling choice we implemented because we wanted it to be easier to take advantage of the visualizer and not have the lines of communication point to different stations every time, and we wanted to be able to name our stations after cities. To test this predicate, we ensured that the predicate would hold when called with the other 2 predicates (validStations and defineStormEdges). Lastly, since it was a bit difficult to test reachability in validStation because it always returned failure, and we weren't sure how to fix our predicate, we decided to verify the parent chain for both branches of the tree, to ensure the nodes were all connected and set the foundation for propagation of information.

defineStormEdges :The first thing we wanted to test was the pre-state before storm propagation. It was imperative that no nodes had access to the information at the beginning, with the central hub having it. We also tested how it would run with our  prior predictions. The last two tests target the post-state of the information being given. We wanted to ensure that the root node was the only node to directly receive the information returned by our storm boolean, so that propagation could start strictly from the AtlantaCentralStation. And we checked that after a successful propagation, all stations would eventually receive the information. It was important to test propagation thoroughly because we would never want all stations to just have the information during the initial state, because it contradicts our objective. If there is no propagation, then all stations could point to the storm information directly and would fit our goals of saving time and trying to create a network of communication.
