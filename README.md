# CSCI 1710 Final Project

This is our `README` for our CSCI 1710 Final Project.

Questions

# Discuss your goals and modeling choices (including the "three buckets": core, closely related, and unrelated).
Our overall goal in this project is to model a distributed system of weather stations sharing information about a storm, and considering the ways in which information propagation can be hindered by various issues in a network, such as nodes failing or behaving in a byzantine manner.
# Core Bucket
We modeled weather stations as sigs with numerous data fields. A core one is information about a storm, which we model as a boolean to indicate whether or not a storm is coming. We also include information about which nodes are the parents of the given node that will propagate information to it.
In order to model failure modes, we also in weather station representation include a mutable field representing a boolean for if the node has failed or not. To then demonstrate a way to deal with failure modes, we also include a partial function mapping to allow nodes to get information from backups when a node fails. In tandem, we model a heartbeat protocol to allow for failure detection, where if a node does not receive a heartbeat from one of its parents, it will then start using the relevant backup.
Finally, we model byzantine behavior with a boolean to indicate whether or not the node is byzantine, and if so then it propagates the opposite of whatever storm information it should be propagating. We then also ensure each node has multiple parents from which to receive information and require it to have a majority vote of parents before propagating information in a way to mitigate the effect of byzantine nodes.
# Closely Related Bucket
While we did use temporal Forge to model message passing and transmission over a network, the model was highly simplified, with all nodes able to communicate consistently over a single timestamp. As an extension, it could be interesting to make the system more realistic by using a more realistic network module, modeling different and inconsistent message times between nodes. It also would allow us to explicitly model omission failures, where a node responds to heartbeat information but fails to receive a message about weather data.
Furthermore, our model as it stands currently only supports one round of iteration. It could be interesting to explore a multi-round model with different potential storms, which would also allow for more interesting ways to handle faults and byzantine behavior; for example, if a node consistently propagated information that contradicted the other parents of a given node, it may decide to switch to the backup for the questionable node.
# Unrelated Bucket
We choose to not model the complex calculations that are involved in real-world weather data, as the core of our model is about a distributed weather system and dealing with faults and byzantine behavior rather than mathematical issues or failed calculations. Such challenges naturally exist in the real world, but are not related to the core idea of our model, and thus we omit consideration of them in the code.
Furthermore, initially one of goals, we decided that modeling hierarchies of stations, including lead regional stations and master stations, was unrelated to the core goal of modeling a fault- and byzantine-tolerant distributed system of weather stations. Adding in the hierarchies would simply create mini subnetworks of stations that would handle failures and byzantine behavior, and then in the larger overall network this same handling would be necessary, just with the regional stations as the individual nodes now. We realized that implementing this functionality would not add to the core part of our model and would instead add additional complexity without the ability to necessarily glean additional meaningful insights.
Additionally, to mathematically achieve full tolerance to failures and byzantine behavior (based on the number of nodes), consensus algorithms such as Paxos or Raft would be necessary. While these algorithms are clearly worthwhile and used in general distributed systems industry scenarios, they are frequently not deployed due to concerns about efficiency and overhead. Rather than implementing a known algorithm, our goal was instead to model our own way of handling faults and byzantine behavior, exploring ways in which our (simple) technique can succeed and come up short in practice.

# How does your model work?
The model uses Temporal Forge to create individual instances of weather propagation across a network of weather stations. Each weather station is a sig that contains fields for storm storm information ( a boolean that indicates whether a storm is coming), a failure status, a byzantine status, a set of 3-5 parent nodes it receives information from, and a partial function that maps failed parents to backup nodes. In the initial state, the originator nodes have a determined storm value, and over the next several states, non-originator nodes receive storm information for their parent node and rely on a majority vote to determine what information to propagate. This, intentionally, also handles byzantine nodes, which work against the system by sending the opposite of the correct value. Finally, if a node stops receiving a heartbeat from one of its parents, it detects that failure and switches to that parent’s backup node. Finally, in order to make the system dynamic, it was created in a way that permits byzantine nodes and failed nodes to emerge at any state.

# What did you get out of the modeling exercise? Or, in other words, what did you get or learn from the modeling project?
One of the biggest takeaways from this modeling exercise is learning and understanding how weather stations work in real life. We did research on what weather stations are made to be resilient to in order to create our threat model. We learned that the systems and their sensors are built to withstand high winds and extremely high temperatures. These threats wear down the hardware and erode communication efficiency over time. We used this threat model as the motivation for our failsafe predicate and our isByzantine checks for each station. We also learned that weather stations are not as rigid as we implemented in our midterm project. They don't have fixed tree structures where there is one central hub that propagates information in a fixed order.

# What tradeoffs did you make in choosing your representation? What else did you try that didn’t work as well?
We ended up making a lot of tradeoffs. One tradeoff we made was moving from froglet to temporal forge so we could have access to the always and eventually operators and improve our information propagation logic. Most fields had to be changed to become var since they could change in between timesteps. For example a node could fail or become byzantine at any time and the storm information could change as well in a real weather station. Speaking of realism, we had to generalize our model a lot. Instead of using location based stations with fixed tree structure, we used location agnostic stations and allowed every node to be able to be an originator of the information.While we gained flexibility and realism,  we lost the predictability of knowing exactly which node propagates to which. 
In our midterm project we had constrained that each node has one parent, but now we have nodes that can be byzantine or backups. We have a majority vote system which acts as a failsafe for byzantine nodes. Each node now has 3 to 5 parents, so they don't have to blindly trust what their one parent says, but can consult with their 3 to 5 parents on what is the true information. While this measure is good for byzantine nodes, we had to change our reachability constraint that only talked about one parent relationships and use transitive closure to support that each node had a set of either  3 to 5 parents.

# What assumptions did you make about scope? What are the limits of your model?
One of the primary assumptions we made about the scope is that storm information can be reduced to a simple boolean, whether a storm is coming or not. Additionally, we assumed that all nodes can communicate within a single state, which simplifies the entire network significantly by removing the need to model message delays. Related, the model only covers one round of information propagation rather than multiple rounds with changing storm conditions. Moreover, we assumed that any node can serve as an originator of information, rather than enforcing a specific, fixed structure, and that each non-originator node has 3 to 5 parents. 
When considering limits, because the model only supports one instance at a time, there is no way to observe how the system actually adapts over several cycles or changing conditions. Additionally, our model does not distinguish between different types of node failure, as a node is simply marked as failed or not. Finally, a major limit within our model is that byzantine tolerance only holds as long as a minority of parents are byzantine. If a majority are byzantine, then the majority vote breaks down.

# Did your goals change at all from your proposal? Did you realize anything you planned was unrealistic, or that anything you thought was unrealistic was doable?
Our goals slightly changed from our proposal. In terms of foundation goals, we were with minimal issues able to attain the goals of unique per-node information and basic temporal modeling. We decided that our goal of modeling a network of regional weather stations in a larger national weather network was somewhat irrelevant to our primary goal of modeling the distributed system and the handling of failures.
In terms of our target goals, there was some minor change from the plan. We successfully modeled fail-safe measures (using a partial function of mappings from parent nodes to backup parents) and also the fact that any individual node could serve as a hub and originate info. Per the feedback in our proposal, we chose not to focus on the goal of modeling a specific weather event like Katrina.
Finally, in terms of reach goals, we realized that while initially seemingly complex, we could in fact implement some amount of byzantine tolerance without totally restructuring our model, instead through simply changing what were initially atom fields (like one parent) to set fields, like multiple parents, and taking a majority vote. So, we ended up implementing this reach goal given that we decided that one each of our foundation and target goals were not necessarily worthwhile. The visualization was easier than anticipated in that LLMs were exceedingly successful at this task (see more on our AI usage below), so what initially seemed highly daunting turned out to be relatively straightforward. As anticipated, however, gossip protocols appeared to be extraordinarily complex to model properly and effectively, and given the time constraints on the project, we chose not to implement this.

# How should we understand an instance of your model and what your visualization shows (whether custom or default)?
Each instance of the model highlights a single run of information propagation. In the first state, only those stations that originate info will have a determined state, and over time the other stations will receive information from their parent stations and calculate a majority vote. As time goes on, stations may fail, so stations relying on them as their parents will have to resort to backups. The custom visualization highlights this, with the nodes arranged in a circle and arrows drawn to indicate parent and backup relationships; colors to show the information the node has originated or decided on; and shapes to illustrate active, failed, or byzantine status. All of the details are visible in the “Legend” located below the actual model visualization.
